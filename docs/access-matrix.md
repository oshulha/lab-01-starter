# Матриця доступу ЛР04 (Incident, baseline 2-A)

Рівень виконання: добрий. Рядки рівня «Відмінно» позначено як не виконувалось.

Принципал береться лише з `HttpContext.User` (cookie, видана сервером). Роль береться лише з
claim, сформованого під час login. `request.Role`, `ownerUserId` у body та заголовки клієнта
у рішенні не беруть участі.

## Політика HTTP-відмов (крок 3)

| Ситуація | Відповідь | Обґрунтування |
|---|---|---|
| Немає автентифікації | 401 | Немає принципала; не redirect на HTML |
| Автентифікований Reporter запитує чужий інцидент | 404, та сама відповідь, що й для неіснуючого id | Не розкриваємо, що ресурс існує |
| Reporter запитує internal comment (навіть свого інциденту) | 404 | Те саме: внутрішній коментар для нього «не існує» |
| Роль не має права на дію (Reporter-власник: triage; Analyst: update/delete; Administrator: будь-яка дія над інцидентом) | 403 | Дія заборонена ролі; для ресурсу, який Reporter і так бачить, його існування не секрет. Reporter, який не є власником, отримує 404 за правилом вище |
| Дозволена роль, але стан не дозволяє (triage, коли статус не New) | 409 | Рішення за станом ресурсу, а не за суб'єктом |

Політика 404 для чужого ресурсу однакова для details, update, delete та child. Тіло відповіді
чужого й неіснуючого ресурсу має збігатися (окрім `traceId`), це перевіряє A-10.

## Примітки до рішень

- Administrator не має автоматичного обходу ownership: у картці 2-A права на читання чужих
  інцидентів для нього не опубліковано, тому deny.
- Update приймає лише `Title` і `Description`. `OwnerUserId`, `Status`, `Severity` і `Role` в DTO
  немає; зайві поля в JSON ігноруються (A-08a).
- Статус змінює лише сервер через окремий endpoint triage; наступний статус ставить сервер.
- Child resource: коментар дає непрямий доступ до даних інциденту, тому перевірка parent
  incident обов'язкова.
- Triage: додатковий context — поточний статус `New` (інакше 409). Owner не може виконати цю
  transition. Запит не несе role, status чи owner; next status (`Triaged`) ставить сервер.
- Audit: після кожної відмови 403 на triage (власник-Reporter, Administrator) лишається подія
  `authorization.denied` (subject id, action, resource, result, час сервера, trace id). Відмова 404
  для чужого інциденту audit не створює, щоб не розрізнятися від неіснуючого id.
