**Що дано.** Власний коректний T-01 з унікальним title й очищенням, response містить id, Results.Created формує Location, GET деталей уже існує. Підготовлено той самий тест до моменту отримання response. Невдалий приклад для аналізу: тіло має ID A, а Location закінчується іншим випадково створеним Guid B.
 
**Умова.** Додайте до T-01 перевірку зв'язку: 201, ID у тілі, Location=/api/incidents/{той самий ID}, GET за цим шляхом повертає той самий ID. До запуску поясніть, який assertion спіймає невдалий приклад ще до GET. У власному коді покажіть, що Guid створюється для entity один раз.
 
Обов’язкове продовження цього самого завдання. Перед запуском розберіть три статичні відповіді: тіло ID=A/Location=B, тіло ID=A/Location=A/GETID=B, та узгоджена A/A/A; A і B — різні Guid. Самостійно вкажіть перший assertion, який має відхилити кожний неправильний випадок, і залежність значень між перевірками. Після запуску T-01 подайте фактичні 201/ID/Location/GETID та схему cleanup, яка працює навіть якщо Location непридатний. Перевірте, що тест не виконує GET на зовнішній origin: для absoluteLocation порівняйте origin із локальним клієнтом до переходу. Нових endpoint-ів не створюйте.
 
**Очікуваний результат.** Заголовок і тіло узгоджені, GET — 200 з тим самим id. Тест зберігає очищення створеного запису в finally, навіть якщо перевірка Location впала.
 
Подання самостійного маршруту: Матриця трьох ланцюгів ID; один створений і прибраний ресурс; незалежні oracle.
 
**Критерії успіху.** Студент перевіряє і статус створення, і адресу ресурсу, не підставляє ID із заголовка як oracle для самого заголовка. URL береться від власного локального клієнта, зовнішніх переходів немає. Оцінюють також обґрунтованість нового контролю/моделі з умови, точність трасування та відповідність поданих доказів саме виконаним діям. Статичний прогноз і фактичний запуск явно розділено; правильний результат без пояснення причин не підміняє самостійну роботу.
